Ejercicio Biblioteca is a desktop library management system built for academic institutions. It provides a unified interface for cataloguing books, managing student borrowing, tracking reservations, recording donations, and monitoring reading activity — all backed by a local SQLite database.

## Architecture

The application follows the **Model-View-Controller (MVC)** pattern, separating data access, business logic, and presentation into three distinct layers.

```
EjercicioBiblioteca/
├── Modelo/
│   ├── libro.py         # Book entity
│   ├── usuario.py       # User entity
│   ├── prestamo.py      # Loan entity
│   └── conexion.py      # Database connection and schema bootstrap
├── Controlador/
│   └── controlador.py   # ControladorBiblioteca — all business logic
└── VistaTk/
    ├── sidebar.py
    ├── libros.py
    ├── usuarios.py
    ├── prestamos.py
    ├── reservas.py
    ├── donaciones.py
    └── ranking.py
```

| Layer | Responsibility |
|---|---|
| **Modelo** | SQLite schema definitions, `crear_conexion()`, and entity models |
| **Controlador** | `ControladorBiblioteca` class — all CRUD operations and business rules |
| **VistaTk** | CustomTkinter views; each module renders one section of the sidebar |

The `App` class in `main_tk.py` is the application entry point. It initialises the database via `crear_conexion()`, builds the main window, and delegates section rendering to `cambiar_vista()`.

## ACID guarantees

Each mutating operation in `ControladorBiblioteca` is explicitly documented with the ACID properties it enforces.

**Atomicity** — Multi-step operations commit together or roll back entirely. For example, `realizar_prestamo()` inserts a row into `prestamo` and sets `disponible = 0` on the corresponding `libro` row within a single `conn.commit()`. If either step raises an exception, `conn.rollback()` is called and no partial state is written. The same pattern applies to `devolver_libro()` (marks returned, frees book, inserts fine) and `registrar_donacion()` (creates book and donation record together).

**Consistency** — Business rules are checked before any write. `realizar_prestamo()` queries `disponible` on the book before inserting the loan. `eliminar_usuario()` and `eliminar_libro()` query for active (non-returned) loans and abort with an error message rather than orphaning records. `reservar_libro()` prevents duplicate pending reservations for the same user/book pair.

**Isolation** — SQLite serialises concurrent writes by default. Each controller method opens its own connection, executes its statements, commits, and closes, keeping transaction scope minimal.

**Durability** — Every successful path ends with `conn.commit()` before `conn.close()`. Foreign keys are activated on every connection with `PRAGMA foreign_keys = ON`, ensuring referential integrity is enforced at the database engine level in addition to the application-level checks.

<Info>
  The fine calculation logic in `calcular_multa()` parses loan dates using `"%d/%m/%Y"` format. Loans outstanding for more than 7 days accrue a fine of **$1.00 per extra day**. Loans approaching the 7-day threshold (6 or more days elapsed) surface in `obtener_prestamos_por_vencer()` as early alerts.
</Info>
